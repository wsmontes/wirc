RSS Feed Reader — Architectural Approaches

Como o WIRC deve buscar, interpretar e armazenar feeds RSS/Atom?

Constraints

Todas as abordagens compartilham: SwiftUI (iOS 17+), zero dependências externas, WOM como modelo de dados, JSON file persistence. A escolha é sobre organização interna.

A

FeedManager Monolítico

Uma classe FeedManager faz tudo: buscar HTTP, parse RSS/Atom, converter pra WOM, salvar, gerenciar subscriptions.

Pros

  • Rápido de implementar (~2-3 arquivos novos)
  • Fácil de entender
  • Menos código boilerplate

Cons

  • Difícil de testar isoladamente
  • Cresce mal — cada formato de feed vira mais if/else
  • Não segue o padrão de adapters do projeto
B

Pipeline em Camadas

Camadas separadas que seguem o padrão existente do IRC: FeedFetcher → FeedParser → FeedToWOMAdapter → WOMStore.

Pros

  • Segue o padrão IRCClient → IRCToWOMAdapter → WOMStore
  • Cada camada testável isoladamente
  • Bom equilíbrio entre simplicidade e extensibilidade

Cons

  • ~5-6 arquivos novos
  • Um pouco mais de código de coordenação
C

Protocolo com Plugins por Formato

FeedSource protocol com implementações por tipo de feed: RSSSource, AtomSource, YouTubeSource, GitHubSource.

Pros

  • Extensível — novo formato = novo plugin
  • Suporta pré-processamento específico (YouTube handle → channel ID)
  • Máxima testabilidade

Cons

  • Overengineered pro MVP
  • ~8-10 arquivos novos
  • Risco de abstração errada antes de ter variabilidade real

Minha Recomendação

B — Pipeline em Camadas. Segue o padrão que já existe no projeto (IRC Client → Adapter → Store), é testável, e não overengineer. Se precisarmos de plugins por formato depois, o Pipeline já tem os pontos de extensão certos — é uma evolução natural, não uma reescrita.
